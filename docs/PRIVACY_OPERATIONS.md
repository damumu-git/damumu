# 单人运营隐私工作规程

更新：2026-10-21（Asia/Seoul）。本页区分代码能力与必须在服务器、邮箱和云账号上执行的工作，不构成韩国法律合规认证。

## 当前运营事实和上线前未决事项

- 服务由一名个人在韩国运营，未登记事业者；运营者同时负责隐私及权利请求，未设置独立部门。公开受理邮箱为 `damumuapp@gmail.com`。
- 主服务器在 AWS Seoul `ap-northeast-2`，当前可用区 `ap-northeast-2a`；后台仅由运营者本人在韩国访问。尚未实际核验备份副本所在地域及云账号权限。
- 用户不授权公开真实姓名，因此公开政策只描述真实的个人运营形式及受理窗口，不虚构公司、部门或负责人姓名。这不代表已满足韩国的全部主体及负责窗口披露要求；正式上架前需核定替代披露是否适用、补齐必要联系渠道。Apple 个人开发者和 Google Play 个人账号的实名展示要求不能靠网站政策绕过。
- 最低年龄14岁；注册记录年龄自我确认及政策阅读时间/版本，不冒称身份证件年龄核验。14岁不是韩国民法成年年龄，仍需核对未成年人参与线下活动、监护人同意和有年龄限制活动的运营规则。
- Firebase 依赖仅有 Core/Messaging；无 Analytics/Crashlytics 插件，原生配置显式关闭 Analytics 和 Messaging 自动初始化。外部推送和 Nominatim 默认关闭，客户端发布开关 `EXTERNAL_PROCESSING_DISCLOSURE_APPROVED=false`，API `Privacy:ExternalPushApproved=false`也阻止向旧令牌投递。不能在接收方、国家、项目、时点/方式、目的、保存期、拒绝/撤回及法律依据未核定时打开开关。系统权限和阅读政策不能代替单独的必要选择。
- 开关关闭时，系统推送、外部地区名称转换均不可用；站内通知、WebSocket、基于坐标的附近查询和手动选区可用。未来获准启用后仍须用户逐项选择；FCM只发送通用文案和必要ID，不发送私信正文或精确位置。
- 定位服务还需独立核查韩国位置信息法的条款、同意和可能的申报要求。

## 服务端保存规则

全部期限为自然月，不以90天替代3个月。迁移 `022_privacy_retention.sql` 定义清理函数，不在执行迁移时立即删除内容；新 API 首次启动及此后每小时运行清理。

| 数据 | 起算点 | 期限/处理 |
| --- | --- | --- |
| 消息及图片 | 消息发送 | 3个月后删除消息；无其他有效引用后删除媒体 |
| 活动、报名、群聊与封面 | 最后日程结束或取消；无日程草稿按创建 | 3个月后删除活动及群聊 |
| 举报与证据 | 举报提交 | 3个月；包括未结案举报，运营者必须及时处理 |
| 通知、结束的安全记录、空会话 | 生成、结束或最后更新 | 3个月 |
| 未关联上传 | 上传 | 24小时后清理 |
| 账号认证/资料/个人头像/令牌 | 注销确认 | 立即清除，登录失效；需要手工处理的文件失败会记录错误 |
| 注销账号占位 | 注销 | 默认头像及“注销用户_数字”，满3个月且必要外键解除后删除；不称不可逆匿名化 |
| 管理安全审计 | 记录生成 | 3个月后移除人员/目标ID、trace和自由文本；最小动作事实最长1年 |

近期举报可将历史图片作为必要证据独立保存到该举报3个月届满；普通会话成员不能通过旧链接读取已到期消息的图片。到期数据库内容会物理删除，文件进入 `media_deletion_queue`，删除失败保留任务并重试。需要因有效法律要求保留特定证据时，先评估并依法隔离最少必要副本，不能将全部正常业务改成无限保存。

清理任务失败日志必须检查；不能把启动了定时任务视为删除已经成功。若积压超过500个文件，任务会分批处理，运营者应检查队列并及时处置。App启动清理过期本地消息，退出/注销清理当前账号聊天缓存和内存图片；无法控制其他用户已保存的截图和副本。

## 日常操作

1. 每个工作日检查隐私邮箱。用受限、加密的记录登记请求编号、收到时间、核验状态、请求范围、适用期限、处理与回复日期；不要在工单里复制密码、身份证件或整段聊天。
2. 通过注册邮箱等最少信息核验。需要代理申请时核验授权；按请求类型适用的法定期限处理。网页注销说明现有的“核验后7日内”承诺必须有人执行。延期/拒绝说明原因及后续途径。
3. 关于可识别照片、文字的删除请求，不能只换昵称；检索具体内容、引用、举报证据和备份处理要求并记录结果。
4. 每周检查后台访问、删除失败及队列。仅本人有生产权限；AWS、GitHub、邮箱开启MFA并使用独立凭据。当前Admin静态Key＋Basic Auth仍是测试方案，正式上线前仍需管理员登录、短时会话、RBAC及二次验证。
5. 每月验证备份恢复和注销测试；发生疑似泄露时撤销相关凭据、限制异常访问、保留最少必要证据、评估影响并按适用法律进行通知/报告。不在公开日志中发布用户数据。

## 加密备份安装（需要在AWS手动执行）

仓库提供每日备份脚本和systemd定时器，**当前尚未在AWS安装或启用**。备份会短暂停止API写入以取得同一时段的数据库和图片，再恢复API；安排在韩国时间凌晨4点。仅轮换自身的加密归档，保留30天，不删除旧迁移备份或其他人工归档。

```bash
sudo apt-get install -y gnupg
sudo install -d -m 700 /etc/damumu /var/backups/damumu/scheduled
sudo sh -c 'umask 077; test -e /etc/damumu/backup.key || openssl rand -hex 32 > /etc/damumu/backup.key'
sudo chmod 600 /etc/damumu/backup.key
sudo install -m 644 deploy/systemd/damumu-backup.service /etc/systemd/system/
sudo install -m 644 deploy/systemd/damumu-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start damumu-backup.service
sudo systemctl enable --now damumu-backup.timer
sudo systemctl list-timers damumu-backup.timer
sudo journalctl -u damumu-backup.service --since today
```

单独安全保管恢复密钥，并将加密归档复制到另一故障域；目标地域、访问控制及可能的境外转移应先确认。脚本不会替你配置异地目的地、MFA、邮箱值班或CloudWatch告警，不得在政策中声称这些工作已完成。

恢复前在隔离环境解密并核验：

```bash
sudo gpg --batch --pinentry-mode loopback \
  --passphrase-file /etc/damumu/backup.key \
  --output /安全的隔离目录/archive.tar.gz \
  --decrypt /var/backups/damumu/scheduled/对应归档.tar.gz.gpg
```

解包后使用独立数据库和媒体目录测试。对照注销/删除请求记录重新执行备份之后的请求，并运行当前保留规则，再恢复公开访问；不能把旧备份直接上线复活已注销账号。运行日志建议使用30天轮换，但必须先检查Nginx、Docker与宿主机实际配置；不要记录Bearer令牌、精确位置或完整聊天。安全审计日志的适用保存义务应另行核定。

## 部署顺序与兼容性

先备份并审查 `022`，核对既有迁移后应用，再部署API、网站和新App。旧App没有年龄/政策确认字段，将无法新注册；旧App也无法为私密聊天图片发送认证头，升级前图片可能加载失败。不要只部署API而继续分发旧App。

初次启动清理会删除此前已满期限的数据。API的数据库角色必须对新增表、序列及被清理表具有所需权限；按既有迁移角色和授权约定执行，不以超级用户运行API。完成后检查日志、队列、注册确认、非成员图片拒绝以及注销。
